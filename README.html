AITrailblazer AI Agent Publishing

Turn any expert publication archive into MongoDB-backed agent memory with TripCodes, Rivers, and Gemini-powered research workflows.

Problem

Expert publishers have years of valuable articles, but readers and agents cannot reliably reuse them. Static archive search does not preserve claims, updates, evidence trails, or follow-up context.

Solution

AITrailblazer converts a small seeded publication archive into article records, TripCodes, River links, session memory, and a judge-visible runtime proof package. DeltaSignal is the proof archive; the product is the generalized publisher-memory agent.

Demo Flow

  1. Resolve HUT-RIVER-001 through MongoDB-style TripCode, claim, River, and three article records.
  2. Show the agent plan, source context, River memory, Gemini answer, next actions, and runtime proof.
  3. Ask a follow-up and show second-turn memory from the reader session.

Hosted Runtime

The judge runtime is deployed on Cloud Run at https://aitrailblazer-ai-agent-publishing-rmycwek6ba-uc.a.run.app. The hosted service exposes GET /health and GET /v1/judge-demo for a fresh-browser or curl smoke test. Current hosted proof invokes Gemini live through Vertex AI and invokes the Agent Builder lane through a Google Cloud Agent Search engine over the three seeded River documents.

Usage

AITrailblazer is a publication-memory agent. It lets a reader enter a known TripCode from an article, newsletter, or research note and retrieve the article's source context, claim cluster, River memory, and follow-up path.

Example TripCode Flow

  1. Open the hosted Cloud Run app.
  2. Enter a known TripCode: HUT-RIVER-001.
  3. The agent resolves the TripCode through MongoDB.
  4. MongoDB MCP retrieves three linked River articles, claims, River edges, and prior memory.
  5. Gemini generates a grounded synthesis from the retrieved publisher memory.
  6. The user asks a follow-up: What should I monitor next?.
  7. The agent uses the saved reader session to continue without requiring the TripCode again.

Agent Builder and Gemini Implementation

The judge-proof path is: input TripCode, plan retrieval steps, use MCP context, synthesize with Gemini, write reader-session memory, then answer a follow-up using prior River state.

MCP Server Usage

The MCP proof should show schema, collection, retrieval, or tool-call evidence. The runtime response includes a Runtime Proof panel so judges do not have to infer partner usage.

Use the official MongoDB MCP server through mongodb-mcp-server@latest. Configure credentials only through environment variables, then run make mcp-check and make mcp-run. The server requires either MDB_MCP_CONNECTION_STRING or both MDB_MCP_API_CLIENT_ID and MDB_MCP_API_CLIENT_SECRET. The local runner starts HTTP transport in read-only mode with JSON responses and externally managed sessions so the app can make a direct tools/call request to the official find tool. Set MCP_SERVER_URL to the HTTP transport URL before redeploying the app runtime.

Deployment Setup

Use make deploy-source or make deploy after setting PROJECT, REGION, and the required environment variables. Use a separate Google Cloud project for this competition and link it to the billing account with the available grant credits.

Environment Variables

  • PORT: local or Cloud Run port.
  • PUBLISHING_DEMO_API_KEY: optional demo protection key.
  • PUBLISHING_USE_GEMINI: production switch for Gemini runtime path.
  • GOOGLE_CLOUD_PROJECT, GOOGLE_CLOUD_LOCATION, GOOGLE_GENAI_USE_VERTEXAI: Google Cloud runtime settings.
  • MONGODB_URI, MONGODB_DATABASE: Atlas or local MongoDB settings.
  • MDB_MCP_CONNECTION_STRING: official MongoDB MCP connection string input.
  • MDB_MCP_API_CLIENT_ID, MDB_MCP_API_CLIENT_SECRET: optional Atlas service-account path for official MongoDB MCP tools.
  • MCP_SERVER_URL, MCP_METHOD, MCP_TOOL_NAME, MCP_SESSION_ID: app runtime path to official MongoDB MCP HTTP transport.
  • MDB_MCP_READ_ONLY, MDB_MCP_HTTP_RESPONSE_TYPE, MDB_MCP_EXTERNALLY_MANAGED_SESSIONS: MCP server safety and HTTP compatibility settings.

Data Model

The judge dataset should use three seeded River articles: a prior thesis article, the anchor TripCode article, and a follow-up monitor-next article. Keep the dataset to 1 TripCode path, 3 to 9 claim nodes, 2 to 4 River edges, and 1 to 2 sessions. Do not ingest the full DeltaSignal archive for the first submission.
